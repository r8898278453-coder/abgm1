# Encrypted WhatsApp intake recovery — 14 November 2026 IST

Verified, sender-mapped events now have a durable intake record before canonical inbox/receipt processing. A transient database failure leaves an encrypted snapshot for controlled recovery instead of relying only on provider redelivery. Replay imports the exact saved event; it cannot select new content, recipients or event time, and it never sends an outbound message.

## Ownership, state and migration

server/whatsAppIntakes.ts owns lifecycle/admission/recovery; whatsAppIntakePayload.ts owns normalization and encrypted context; whatsAppIntakeDomain.ts invokes the existing inbox/receipt services. Transaction hooks in whatsAppInbound.ts retain its canonical event/marker/conflict ownership and allow atomic journal/queue settlement. No parallel lead writer, receipt service, scheduler or send path was created.

The production webhook adapter now uses this intake owner. Existing owner Telegram notification remains best effort after a newly committed webhook import; operator replay does not invoke that notification. An uncertain commit can suppress a duplicate notification while preserving the canonical inbox. The former canned promised reply is not generated by this intake adapter; operator-approved sales replies remain separate.

Forward043_whatsapp_intakes adds one table:80 canonical tables; next044. Historical001–042 are unchanged. Schema and existing encryption/auth key configuration must be ready before this adapter runs. There is no new key or production configuration change in this implementation.

States: RECEIVED/PROCESSING → RECORDED, FAILED, CONFLICT, EXPIRED or DEAD_LETTER; human admission uses QUEUED. A failed/unconfirmed intake may already have a canonical record, so failure is not proof that an event was absent. Sender checks and core idempotency apply on every actual import. Original encrypted context is never rebuilt from operator evidence.

Scoped no-store APIs: GET `/api/companies/:companyId/sales/intakes` returns at most50 metadata summaries, recovery work first; POST `/intakes/:intakeId/replay` and POST `/intakes/:intakeId/cancel-replay` require recovery authority and exact revision/evidence. Read-only roles get no payload, recipient, provider reference, key or ciphertext. Replay admission is not execution success.

## Operational boundaries and remaining gates

Logical expiry always prevents operator replay. Physical erasure is a bounded dispatcher maintenance pass, including while global execution stop is active; cron/dispatcher outages can delay erasure. Successful imports erase snapshots in the canonical transaction. Backups, metadata retention, deleted-client policy and full key-recovery operations remain separate P10 acceptance work.

The intake temporarily retains encrypted verified event data, including a changed variant before canonical conflict classification. A rejected conflict snapshot is cleared in the conflict transaction and cannot be operator-replayed; existing conflict review remains the only retain-original path. This supersedes older absolute no-candidate-retention descriptions for the private intake layer only; the conflict observation ledger still stores flags/hashes rather than candidate bodies.

Unmapped/ambiguous senders still return503 without assigning private data to a client. Recovery depends on correcting sender configuration and provider redelivery retention. Genuine verified redelivery can recover an expired/dead-letter intake using the incoming data, while preserving the old provider time; the operator cannot bypass expired/missing/corrupt snapshots or three-admission limits.

General global raw-payload quarantine, automated retries beyond this reviewed budget, live mailbox/calendar providers, all-module reporting/retention and Hostinger release acceptance remain open. No production migration/deployment, environment activation or customer send was performed. Approved sales sending and reel rendering remain default off; billing is excluded.
