| Implemented control | Behavior |
| --- | --- |
| Required retry identity | POST `/api/telegram/notify` now requires companyId, requestKey (64 lowercase hex) and message. Old unkeyed requests are refused; there is no unjournalled HTTP fallback. Deploy matching frontend/backend together. |
| Immutable content/actor | SHA-256 of exact client, current actor and trimmed message binds each key. Changed body or actor on that key conflicts. Body and credentials are not retained. |
| Bound destination | Original bot ID, destination fingerprint and full binding hash freeze the saved integration ID/token/chat tuple. The canonical transport rechecks exact client ownership, unique Telegram binding, current execution access and stop before provider I/O. Changed configuration pauses; it never retargets a request. |
| Durable phases | PREPARED commits with audit before dispatch admission. SENDING commits with audit before calling the provider. API_ACCEPTED, UNKNOWN or PAUSED settlement commits with audit. Commit/audit failures cannot manufacture successful persisted evidence. |
| Single sender | Company-scoped locking serializes admission. Only the original fresh claim can cross PREPARED → SENDING. Same-key calls inspect saved state, including cached acceptance; they never invoke the provider again. A new key with identical actor/content is also refused while an earlier matching request is PREPARED/SENDING/UNKNOWN. |
| Lost acknowledgements | Lost claim ACK starts no provider call. Lost SENDING ACK is quarantined even if no provider call occurred. Lost settlement ACK returns persisted false; a later lookup may establish the committed acceptance. No automatic timeout takeover or resend occurs. |
| Restart recovery | Read APIs recover exact saved status independently of the original HTTP process. PREPARED may be cancelled; SENDING and UNKNOWN remain under investigation. There is no automatic resumption of an interrupted manual request. |
| Versioned cancellation | POST `/api/companies/:companyId/telegram-manual/:key/cancel` requires expectedVersion and current execute authority. Only PREPARED can become CANCELLED. Same-version cancellation replay reconciles the prior cancellation without another transition/audit. SENDING/UNKNOWN/accepted requests cannot be cancelled as though unsent. |
| Budget/resource control | Existing shared client MESSAGE budget is used with a Telegram-specific key namespace. Per-client admission is capped at100 new rows per IST day and1,000 retained rows; replay does not consume another slot. No automatic deletion of uncertain evidence is introduced. |
| Private status/history | GET `/api/companies/:companyId/telegram-manual/:key` and `/telegram-manual?before=...` require current read permission. Read-only SQL deadlines apply. History returns25 rows plus a validated time/key cursor. No body, raw chat ID, token, input/binding hash or claim token is exposed. |
| Strict response truth | Persisted success requires exact company/key, saved API_ACCEPTED state and valid provider message ID. Telegram message ID and sender/destination evidence are not delivery/read proof. A reused accepted request explicitly starts no new send. Known PAUSED/CANCELLED states stay distinct from uncertain effects. |
| UI retry/reload | Existing actor/client-scoped retry-key helper stores only hashes/key. A last-request pointer restores status after page reload. No plaintext body is put in browser storage. Incomplete ACK or unresolved persisted state locks further sends in the view; metadata reload does not clear it. |
| Operator UI | Manual journal displays state, timestamps, original bot/destination fingerprint and accepted provider ID. Prepared-only cancellation, scoped paging and reload reuse canonical APIs. Viewers can inspect but not mutate. Client/session changes fence delayed status/cancellation responses. |
| Canonical transport | `sendTenantTelegram` remains the boolean wrapper for existing scheduled/internal consumers. The new detailed attempt owner exposes actual provider message ID for manual journal settlement. Both use the same exact Telegram ACK and final stop/configuration boundary. No real provider call was made in tests. |
