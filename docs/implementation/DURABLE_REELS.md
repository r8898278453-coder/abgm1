# Durable reels and asset approvals — 12 November 2026 IST

Reel state now lives in the existing SQL job_queue and its transactional action ledger/outbox. The memory manager has been removed. Rendering remains disabled by default; no hosting setting, production database, dispatcher schedule or provider configuration was changed.

## Delivered behavior

- POST /api/ai/render-reel authenticates an active writable client, validates exactly three bounded scenes and requires a64-hex Idempotency-Key. Company lock plus a short database advisory admission lock serialize admission. Same actor/key/intent returns the saved job, including a completed result; changed intent conflicts. Unknown acknowledgements retain the same browser retry identity. Deliberate new attempts after a confirmed terminal result get a new identity.
- A maximum of8 active jobs per client and64 per database prevents an unbounded active backlog. The job payload contains a strict versioned snapshot, server actor, canonical business name, color, draft scenes and approved asset IDs/revisions/hashes. It contains no image binaries or credentials. Manual draft text is not promoted to verified business facts or publication approval.
- The registered reel_render handler uses the existing claim/retry/heartbeat/lease recovery system. Crashed RUNNING jobs become claimable after the existing five-minute lease expiry, up to three real attempts. Disabled capability and occupied render capacity defer without consuming the failure budget. No generic public queue payload can bypass the internal reel admission schema.
- GET /api/companies/:companyId/reel-jobs and the existing status route read SQL on every request. Status requires an explicit companyId query; all reads use current client authorization. History puts active jobs first and returns up to18 bounded metadata rows, covering the eight active jobs and ten terminal rows. Payloads, scripts, actor identity and raw errors are excluded. RUNNING progress is unknown/null; only committed success is100 percent.
- POST /api/ai/render-reel/:jobId/cancel fences QUEUED, RETRY_WAIT and RUNNING jobs and appends the cancellation event atomically. Repeated cancellation is idempotent. Cancellation immediately fences persistence; process termination is observed by the worker, not promised synchronously by the HTTP acknowledgement.
- One SQL advisory CPU slot per database is held on a dedicated connection until the rendering process exits. Role/assignment, archive, canonical name, approvals, lease and slot ownership are rechecked during execution and at settlement. A stale or revoked worker cannot publish a successful artifact. Existing global emergency stop also blocks settlement.
- Rendering runs in a detached Linux process group with a minimal environment that excludes DB/provider variables. An IPC ready handshake prevents dropped startup messages. Parent cancellation kills the group and waits for the renderer exit before releasing capacity. The child also stops its group on parent IPC disconnect and has an independent three-minute watchdog.
- Limits: three-minute wall deadline, one Remotion frame worker,512-MiB Node heap,768-MiB sampled process-group RSS threshold (500-ms sampling),50-MiB output cap,256-MiB completed reel budget per client,2-GiB completed reel budget per database upload root,100-MiB free-disk reserve and bounded storage scans. RSS/output monitoring is sampled, not a kernel cgroup limit; transient overshoot and processes escaping the group are not claimed impossible. Deployment should also enforce OS/container limits where available.
- Output starts in a private .reel-staging directory. File signature/size, current context and approvals are checked before an atomic move into generated marketing uploads within lease-fenced completion. Lost SQL commit acknowledgement reconciles the durable result before deleting any artifact. Failed/cancelled staging is removed; abandoned renderer-owned staging directories older than24h are cleaned on the next eligible worker run. Completed referenced videos are retained; quota exhaustion blocks new work rather than deleting customer content. Disk quotas cover reel files; other uploads still need their own retention policy.

## Asset review

Forward036_render_asset_approvals adds one canonical table (64 total). Historical001–035 are unchanged; next migration037.

GET/POST company asset-approvals routes use current agency read/approve permissions. Approval is a compare-and-swap revision, tied to the current locally read PNG/JPEG/WebP content hash and a required rights/source declaration. Revocation works without a readable original. The approval decision/revision/hash and reviewer are appended to the existing agency audit transaction. The current declaration is stored with the approval. This is an operator declaration, not legal verification of copyright.

Both creative and reel routes select only approved local assets; an explicit unapproved image is rejected. New renders recheck bytes; changing a file invalidates its earlier approval. Reel workers also reject approval revision changes during execution/settlement. Legacy remote or SVG assets require a local supported raster upload and review. Empty approved image libraries use a solid background, without invented stock images. Recorded APPROVED list metadata is not a fresh on-read byte check. Existing generated marketing URLs remain public and revocation does not recall an already downloaded/published artifact.

Content Studio includes asset review with retained conflict state, saved job history, reload recovery, cancellation and explicit selection of completed videos. Client/session remount and request guards exclude obsolete results. Polling avoids overlapping requests and reports unavailable status without declaring completion. New render admission clears the previous video's selection, preventing a failed new render from silently attaching the older video to a new draft. Saved timestamps display Asia/Kolkata.

## Worker operation and capability gate

Build produces dist/server.cjs, dist/reel-worker.cjs and dist/reel-queue-worker.cjs. npm run worker:reels processes at most one registered reel job per invocation, verifies canonical schema without migrations, and closes its SQL pool. It can be scheduled on a capable worker independently of HTTP request timeouts. The existing dispatcher also knows the reel job type; avoid enabling CPU rendering in a shared web process with an unsuitable request/runtime budget.

Activation requires explicit ENABLE_REEL_RENDERING=true, Linux process-group and /proc support, an installed executable at absolute REEL_BROWSER_EXECUTABLE, the compiled worker, the Remotion source/composition and dependencies/fonts, and writable persistent uploads shared with the web process. The upload root and database must refer to the same deployment. No automatic Chromium download is used when an installed executable is supplied. A worker using another machine requires shared artifact storage; copying DB credentials alone is insufficient. Hostinger process/Chromium/cron limits and the deployed schema remain unverified. Keep the flag off there until these prerequisites are demonstrated.
