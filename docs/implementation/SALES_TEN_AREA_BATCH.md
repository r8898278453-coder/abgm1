## Data ownership and compatibility

Forward037_sales_workspace adds six tables: sales_client_policies, sales_contact_permissions, sales_inbox_messages, sales_opportunities, sales_qualifications and sales_prospect_imports. Schema target037/70 tables; historical001–036 are unchanged; next038. There is no automatic production migration. APIs mount once through server/salesRoutes.ts; existing CRM stage rows, message intents, webhook markers and knowledge facts remain canonical owners. The new knowledge SQL reader reuses the existing fact eligibility/source-revision rules inside the sales transaction rather than copying them.

New routes are under /api/companies/:companyId/sales and /api/agencies/:agencyId/sales-overview. Every route authenticates, uses explicit company/agency scope, returns no-store and fixed safe failures. Mutation services recheck current agency role and active client inside their company-lock transaction. Policy/consent requires manage; opportunity/qualification/import/link requires write. Viewer and unrelated-agency writes are refused. Saved revisions plus explicit reload prevent unknown acknowledgements being shown as success; prospect imports retain actor/client/input retry identity.

The existing verified WhatsApp webhook sender mapping and processed marker still protect intake. Marker, identity selection, message, opt-out and audit commit together. A repeated message event cannot repeat ingestion or opt-out increments. Multiple plausible leads do not trigger an automatic merge; a human can link the inbox event without editing historical provider data. Attachments retain bounded IDs/type metadata only; no external attachment URL is fetched here. Legacy processed events are not backfilled with fabricated message bodies.

Outbound text is saved before the shared message-intent/provider boundary. If permission or policy is unavailable, no send occurs. The low-level Meta adapter also checks explicit client policy, so publishing cannot bypass contact suppression. Existing unreviewed autonomous WhatsApp sends are now paused. To resume an eligible manual send, an authorized operator must record real permission evidence and satisfy window/policy/cap prerequisites. An inbound inquiry alone does not imply marketing consent. Consent changes cannot recall an in-flight request; this timing limitation is explicit rather than an exactly-once delivery claim.

CSV import keys serialize retry attempts and preserve row outcomes. Data is parsed, not evaluated; source text is an operator declaration, not verified legal authority. Source/contact data is client-private SQL, not public uploads. No third-party enrichment, paid import or LinkedIn action is activated. New private tables need the wider retention/deletion/export review under P10-01.

## Screens and honest reporting

CRM includes saved policy/ICP, contact permission/evidence, outcome/next action in IST, qualification/handoff, CSV results, inbox/link/history and dated sales reporting. Agency settings include current exceptions and client selection. Late reads/writes from an obsolete selected client/session are discarded; a failed write keeps the draft and requires saved-state reload. Forms expose read/write/manage controls returned by canonical policy.

Reports separate selected-day immutable activity from current backlog and current, potentially truncated manual attribution. Manual deal values never become verified revenue; currencies are not combined and ROI is null. No activity is inferred from a link opening, a draft, a page reload or a successful-looking UI animation.
