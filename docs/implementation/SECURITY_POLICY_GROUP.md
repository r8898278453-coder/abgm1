## Cookie transport and revocation

Cookie transport is opt-in: server AUTH_COOKIE_ENABLED=true, frontend VITE_AUTH_SESSION_MODE=cookie, canonical HTTPS PUBLIC_APP_URL and correctly trusted proxy hops must be verified together. No flag or hosting setting was enabled here. Existing bearer clients remain compatible and intentionally send no ambient cookies. Actual Hostinger/HTTPS/proxy/canary acceptance remains P00/P10 work.

The server issues __Host-abgm1_session with HttpOnly, Secure, SameSite=Strict, path=/ and no Domain. A negotiated cookie response returns only session metadata/CSRF, not the JWT. Browser storage retains an actor/session-change marker and CSRF token, not that cookie JWT. JSON/AI/file/download transports share the mode. Session change/logout purges existing private browser state; late responses refuse. Without a local cookie-mode marker requests omit cookies, including after an offline local logout. GET auth/me can recover CSRF for a marked current cookie session. Public login/register with a residual cookie require the canonical Origin, allowing intentional re-login after local state was cleared; other unsafe cookie requests additionally require a session-bound HMAC CSRF token. Duplicate cookie names and malformed Unicode/header values refuse safely. Explicit bearer authority takes precedence and never falls back to a cookie.

POST auth/logout revokes the current jti before acknowledging. POST auth/logout-all accepts exactly {} and increments a persistent user epoch. Every authenticated token checks current password material, jti revocation and epoch; old tokens without an epoch mean0 and stop working after a revocation increment. Fresh login loads the current epoch. JWT role claims never establish platform-admin or agency grants; SQL user/membership/assignment policies remain authoritative.

DB-clock limits allow25 IP admissions/15 minutes and10 normalized-account admissions/15 minutes. Scopes are SHA256; blocked IPs stop before account admission. These count login attempts, not just failures. The existing process-local five-failure lockout remains an additional separate rule. Bounded pruneSecurityState removes at most100 expired revocation/state rows and old32-day limit rows per table/call; it does not delete user epochs. It is an explicit maintenance helper, not a claimed deployed cleanup cron.

## OAuth and encryption boundaries

OAuth lifecycle helpers are internal building blocks, with no public authorization/callback route in this group. PKCE state uses a random43-character nonce, only its SHA256 in SQL, encrypted verifier and exact actor/company/provider/session binding with10-minute DB expiry. Consumption locks the state, checks current management/active-client policy and clears verifier material on the single successful consume. Eight concurrent consumes have one winner. No code/token exchange occurs in these tests or helpers.

Refresh acquisition grants one60-second lease per client/provider. A refresh result can commit only under the current unexpired lease and an unchanged sealed credential snapshot. Only bounded token-related fields are accepted; account/location and unrelated stored fields survive. Values are encrypted; caller ciphertext is rejected. Lease loss/manual credential changes refuse. Status remains saved/unverified. Provider adapters must still authorize their caller, perform bounded provider-network requests and handle revoked/expired tokens before enabling work.

CREDENTIAL_ENCRYPTION_PREVIOUS_KEYS optionally supplies a JSON array of at most3 previous secrets for bounded legacy AES-GCM decryption after an operator key change. New encryption uses the active startup key. Malformed ciphertext returns unavailable; raw crypto errors/secrets are not logged. No keys were configured or rotated here; full operational re-encryption/key recovery remains a separate gated task.
